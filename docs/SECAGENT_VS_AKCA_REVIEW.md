# SecAgent versus AKCA: codebase review

Reviewed 24 September 2026. SecAgent refers to the current working tree, including ten pre-existing uncommitted source changes. AKCA refers to the public `main` branch as exposed on GitHub at review time. This is a static implementation comparison, not a measured detection-rate or performance benchmark. No live target was scanned. GitHub was reachable through the web reader but not from the local shell, so AKCA could not be cloned or tested locally. AKCA implementation conclusions below are limited to the source and documentation linked here.

## Executive assessment

SecAgent is a broad offensive automation framework with Python orchestration, optional third-party recon tools, deterministic probes, LLM validation, memory, Go utilities, and native components. AKCA is a focused Go DAST scanner with browser and API discovery, per-module proof policies, bounded execution controls, persisted evidence, and multiple report formats. The distinction matters: SecAgent has broader potential workflow scope; AKCA has a more coherent, inspectable web-scanning path today.

The largest SecAgent concern is the gap between advertised capability and the `secagent scan` path. The primary DAG has four tasks (recon, universal scan, validation, report); the universal task routes to the same recon handler, so the intended `scan_handler` is not invoked by that task. The separate API, browser, Web3, and specialized web agents are not registered in this DAG. The pipeline does run optional Arsenal probes and the Crucible stage, but the advertised scan breadth should not be interpreted as breadth exercised by the default command. See [`armada/swarm.py`](../python-agents/secagents/armada/swarm.py), [`armada/handlers.py`](../python-agents/secagents/armada/handlers.py), and [`pipeline/runner.py`](../python-agents/secagents/pipeline/runner.py).

AKCA's claimed advantage is evidence quality, and its repository has concrete [module proof-policy code](https://github.com/akha-security/akca/blob/main/engine/internal/verification/proof_policy.go), a [verification package](https://github.com/akha-security/akca/tree/main/engine/internal/verification), and a [false-positive audit](https://github.com/akha-security/akca/blob/main/engine/docs/FALSE_POSITIVE_AUDIT.md). That establishes an implemented policy framework, not a proven superiority in real-world detection. Neither project was run against the same controlled corpus here.

## SecAgent strengths

1. **Useful framework breadth.** The repository contains working implementations or substantial scaffolding for the CLI, worker, Redis and Rust scheduler, Go recon, C++ bridge, Python agents, playbooks, memory, sandbox wrapper, replay capsules, and notification hooks. This can serve red-team workflow development beyond a single web scanner. See [`cli.py`](../python-agents/secagents/cli.py), [`worker/runner.py`](../python-agents/secagents/worker/runner.py), [`rust-core/src/main.rs`](../rust-core/src/main.rs), and [`operational/playbook.py`](../python-agents/secagents/operational/playbook.py).
2. **Strong ecosystem composition potential.** `ExternalTools` invokes subfinder, httpx, katana, waybackurls, nuclei and naabu concurrently when binaries exist. That can immediately leverage well-known tools and allows partial operation if one is absent. See [`external_tools.py`](../python-agents/secagents/modules/external_tools.py).
3. **Fail-closed initial scope policy.** Without `ALLOWED_DOMAINS`, the Python entry path refuses a scan; `BLOCKED_DOMAINS` is checked first. A Go scope check exists too. This is a meaningful safety default even though redirects remain a gap. See [`scope.py`](../python-agents/secagents/infra/scope.py) and [`subdomain.go`](../go-services/recon/subdomain.go).
4. **Deterministic checks are present.** CVE check definitions use canaries, signatures and response metadata for classes such as SQLi, XSS, SSTI, LFI, exposure and headers. These are more concrete than an LLM-only scanner. See [`cve_checks.py`](../python-agents/secagents/modules/cve_checks.py) and [`cve_scanner.py`](../python-agents/secagents/modules/cve_scanner.py).
5. **Provider flexibility.** `OmniLLM` supports several hosted APIs and an Ollama endpoint, and `ConsensusEngine` can gather multiple votes. Useful as a research assistive layer when configured, though votes are not independent exploit proof. See [`omni.py`](../python-agents/secagents/llm/omni.py) and [`consensus.py`](../python-agents/secagents/llm/consensus.py).
6. **Operator-friendly CLI and artifacts.** The CLI gives a readable summary and JSON/Markdown/HTML outputs; regression records, Hermes memory, and Jira/Slack hooks can help an operator track findings. See [`cli.py`](../python-agents/secagents/cli.py), [`reporter.py`](../python-agents/secagents/remediation/reporter.py), and [`ci_notifier.py`](../python-agents/secagents/engine/ci_notifier.py).
7. **Simple local API for experimentation.** Python agent classes and tools are easy to call directly or extend. The browser agent, Web3 agent, keyhacks scanner and playbooks may be useful as standalone components even though the default scan does not exercise all of them.
8. **Some real concurrency and graceful fallback.** The CVE scanner shares an `httpx.AsyncClient` and caps work with a semaphore. The native bridge falls back to Python regex/socket calls when the C++ library is unavailable. See [`cve_scanner.py`](../python-agents/secagents/modules/cve_scanner.py) and [`native.py`](../python-agents/secagents/core/native.py).

## SecAgent weaknesses and risks, ordered by impact

### Critical: operational truth and scan correctness

1. **Primary DAG misroutes the universal scan.** `Orchestrator.decompose_intent(SCAN)` creates `universal_scan` on `security_orchestrator`; `ArmadaOrchestrator.plan_mission` remaps it to `web_crawl`, whose registered handler is `recon_handler`. The `universal_scan` handler returned by `build_scan_handlers` is registered under a name that the default graph does not use. This means the intended CVE scanner and nuclei/naabu scan phase are bypassed in the normal DAG. An additional `report` task is routed to `validator`, so validation can run twice. Evidence: [`orchestrator.py`](../python-agents/secagents/core/orchestrator.py), [`swarm.py`](../python-agents/secagents/armada/swarm.py), [`handlers.py`](../python-agents/secagents/armada/handlers.py).
2. **MCP scan and PoC verification return fabricated outcomes.** `_handle_scan` always says completed with zero findings; `_handle_verify_poc` always returns `verified: True`; the target DNA handler refers to fields/methods that do not match the current memory API. Clients can receive false success. See [`mcp_server.py`](../python-agents/secagents/mcp_server.py).
3. **Default scan misses advertised agents.** `APISecurityAgent`, `BrowserAgent`, `Web3SecurityAgent` and the SQLi/XSS/SSRF/IDOR specialist handlers are absent from the four-task default graph. A class existing in the repository is not the same as scan coverage. See [`swarm.py`](../python-agents/secagents/armada/swarm.py), [`handlers.py`](../python-agents/secagents/armada/handlers.py), [`runner.py`](../python-agents/secagents/pipeline/runner.py).
4. **“Zero false positives” is not supportable.** Crucible's deterministic replay fetches `poc_url` with GET and searches the returned body for `proof_signal`. But many `proof_signal` values are explanatory strings such as `DB error signature: ...`, `Missing: ...`, or `ACAO reflects ...`, rather than literal response bytes. Header-only, POST and timing findings may therefore be rejected even when valid. For other findings, a plain payload echo or body substring can pass without a clean baseline or negative control. LLM agreement is an opinion layer, not exploit verification. See [`validation.py`](../python-agents/secagents/crucible/validation.py) and [`cve_checks.py`](../python-agents/secagents/modules/cve_checks.py).
5. **Unverified findings can be overclaimed by a second validator.** `ValidatorAgent._replay_poc` treats any response below 500 as valid for a finding marked deterministic/validated even if the proof signal is absent. The later Crucible is stricter, but this weakens the DAG's intermediate validated set and can mislead direct users of `ValidatorAgent`. See [`validator.py`](../python-agents/secagents/agents/validator.py).

### High: target safety, control and evidence

6. **Scope is checked before requests, not across every redirect.** Main clients in Crucible, CVE scanner, browser fallback, and web agent enable redirect following; the Go crawler accepts redirects without rechecking destination. The initial host gate does not prove every network request remains authorized. See [`scope.py`](../python-agents/secagents/infra/scope.py), [`validation.py`](../python-agents/secagents/crucible/validation.py), [`crawler.go`](../go-services/recon/crawler.go).
7. **The default Fortress setting does not isolate scanning.** `ScanPipeline` constructs a `FortressSandbox` and checks for an image, but its agent and tool calls run in the host process; the only subsequent sandbox use is a log write. The flag/README can suggest isolation that does not occur. See [`runner.py`](../python-agents/secagents/pipeline/runner.py) and [`sandbox.py`](../python-agents/secagents/fortress/sandbox.py).
8. **No enforced global HTTP budget.** `--depth` and `--workers` are coarse controls; external subprocesses have per-tool timeouts, but there is no shared request counter, per-host rate cap or total duration limit across the default scan. The token `BudgetGuard` is defined but not imported or called by the LLM client or pipeline. See [`cli.py`](../python-agents/secagents/cli.py), [`external_tools.py`](../python-agents/secagents/modules/external_tools.py), [`budget_guard.py`](../python-agents/secagents/infra/budget_guard.py), [`omni.py`](../python-agents/secagents/llm/omni.py).
9. **API heuristics are unsafe as vulnerability proofs if used directly.** The API agent calls a 200 response on a changed object ID “BOLA,” a 200 response without auth “auth bypass,” and a successful write “mass assignment”; those lack identity and state controls. It also sends ten rapid requests per endpoint and marks absence of 429 as missing rate limiting. POST/PUT/PATCH/DELETE tests can mutate target state without an operator-provided cleanup contract. This agent is not currently in the default scan path, which limits the immediate exposure but also limits coverage. See [`api_security.py`](../python-agents/secagents/agents/api_security.py).
10. **Proof artifacts can misrepresent reproduction.** `PoCGenerator` treats any response difference or payload reflection as success, can replace intended methods with POST, and emits `verify=False` / `curl -k`. Proof capsule replay also disables TLS verification and checks only for a response substring; it does not validate scope, state, or original proof context. See [`poc_generator.py`](../python-agents/secagents/engine/poc_generator.py) and [`proof_capsule.py`](../python-agents/secagents/operational/proof_capsule.py).
11. **Results omit important evidence and coverage state.** The HTML output is a severity/title/URL table; JSON has no versioned evidence schema; the pipeline does not report skipped tools, failed DAG tasks, request counts, or incomplete coverage in the final deliverable. `cli.py` prints “No vulnerabilities detected” when the list is empty even if work was skipped. See [`reporter.py`](../python-agents/secagents/remediation/reporter.py), [`runner.py`](../python-agents/secagents/pipeline/runner.py), [`cli.py`](../python-agents/secagents/cli.py).

### Medium: reliability and maintenance

12. **Findings are deduplicated by URL and type only.** Distinct parameters, payloads, methods and proof can collapse into one result before Crucible. See [`runner.py`](../python-agents/secagents/pipeline/runner.py).
13. **Native architecture is mostly optional to the default scan.** The C++ matcher compiles a `std::regex` for each call, which does not itself establish SIMD acceleration. The Python bridge falls back to `re`; Rust has a separate Redis workflow listener rather than an in-process hot path for the CLI scan. Benchmarks would be needed before claiming speed superiority. See [`fast_matcher.cpp`](../cpp-core/src/fast_matcher.cpp), [`native.py`](../python-agents/secagents/core/native.py), [`rust-core/src/main.rs`](../rust-core/src/main.rs).
14. **Multiple overlapping pipelines complicate reasoning.** The repository has `ScanPipeline`, `Autopilot`, `Orchestrator`, `ArmadaOrchestrator`, specialized agents, CVE checks and Arsenal scanners. Some are used only indirectly or separately. This increases integration and test burden, and makes README feature lists a poor proxy for default behavior.
15. **Cross-platform integration is uneven.** The external tool runner uses shell command templates and a Unix-specific `echo ... | waybackurls`; several components are optional binaries, while the Python package manifest alone does not install them. The generated Python PoC imports `requests`, which is not a declared package dependency. See [`external_tools.py`](../python-agents/secagents/modules/external_tools.py), [`poc_generator.py`](../python-agents/secagents/engine/poc_generator.py), [`pyproject.toml`](../python-agents/pyproject.toml).
16. **CI/test gates have a configuration defect.** The Go crawler test starts an `httptest` server but does not set `ALLOWED_DOMAINS`; current crawler scope enforcement returns zero results, so `go test ./...` fails without an environment override. The CI Go job calls `go test` with a repository-wide `ALLOWED_DOMAINS=example.com,*.example.com`, which still excludes localhost. Locally, the test passed after overriding to `127.0.0.1,localhost`. See [`recon_test.go`](../go-services/recon/recon_test.go), [`crawler.go`](../go-services/recon/crawler.go), [`ci.yml`](../.github/workflows/ci.yml).
17. **Some claims exceed the code.** The README advertises multi-attempt Crucible validation and strict SSL enforcement; the sampled Crucible method makes one GET, while browser context and proof replay explicitly ignore TLS errors. The README's “150+ tools” catalog is separate from the ten `ExternalTools` command templates used by Autopilot. See [`README.md`](../README.md), [`validation.py`](../python-agents/secagents/crucible/validation.py), [`browser_agent.py`](../python-agents/secagents/agents/browser_agent.py), [`proof_capsule.py`](../python-agents/secagents/operational/proof_capsule.py), [`external_tools.py`](../python-agents/secagents/modules/external_tools.py).

## AKCA advantages relevant to this comparison

The public repository exposes an [evidence policy implementation](https://github.com/akha-security/akca/blob/main/engine/internal/verification/proof_policy.go) with required observation roles, independent runs, native baseline, negative control and state proof fields. The [audit document](https://github.com/akha-security/akca/blob/main/engine/docs/FALSE_POSITIVE_AUDIT.md) explicitly distinguishes proof classes and says single status changes or payload echoes are insufficient. Its [feature guide](https://github.com/akha-security/akca/blob/main/FEATURES.md) describes preserving real browser requests, HTTP methods and API schemas; the [README](https://github.com/akha-security/akca) documents scope, budgets, session inputs, several output formats and replay. Together these form a clearer DAST evidence and operator-control story than SecAgent's current default path.

## AKCA limitations and caveats

1. **Narrower mission.** AKCA is primarily web/API DAST. It does not advertise SecAgent-style multi-agent orchestration, local LLM selection, Web3 review, exploit-chain reasoning or red-team playbooks. A team needing those workflows may still want SecAgent components alongside it.
2. **Early release and uncertain field accuracy.** The public guide identifies the project as an early `v0.2.x` release and explicitly says no scanner guarantees complete coverage or zero false positives. This review did not run its benchmark or reproduce its detection claims. [Source](https://github.com/akha-security/akca/blob/main/FEATURES.md).
3. **Browser and advanced proof prerequisites.** Browser checks require a supported local browser; OAST, runtime sensors, extra identities and state policies are conditional. Thus a default invocation cannot exercise every listed check. [Sources](https://github.com/akha-security/akca), [features](https://github.com/akha-security/akca/blob/main/FEATURES.md).
4. **Traffic can still be substantial.** AKCA's README says the module scan has no request quota by default; users must set request/crawler/time budgets and rate limits for predictable load. Its `passive` profile still sends discovery requests. [Source](https://github.com/akha-security/akca#scope-and-scan-limits).
5. **Sensitive report handling needs review.** The current README states exports do not automatically mask raw credentials and cookies, while the feature guide says automatic redaction protects secrets. Treat the README's warning as the conservative operational assumption until verified against the exact export path. [README](https://github.com/akha-security/akca#reports), [feature guide](https://github.com/akha-security/akca/blob/main/FEATURES.md).
6. **Larger focused engine carries maintenance cost.** The source tree has many internal packages and check families. Broad check count raises regression and fixture maintenance needs. It is a reasonable inference from the repository structure, not a measured quality defect. [Source tree](https://github.com/akha-security/akca/tree/main/engine/internal).
7. **Installation constraints.** Source install currently documents Go 1.25+, and browser-backed checks need Chrome/Chromium/Edge. Prebuilt binaries ease this, but advanced checks still have local prerequisites. [Source](https://github.com/akha-security/akca#installation).

## What I verified

- Inspected the local Python scan path, agents, validation, reports, scope, MCP, memory-related wiring, external tools, native bridge, Rust workflow listener, Go crawler and CI definitions. This was a codebase-wide map with deep review of the critical execution path, not line-by-line inspection of every file.
- Python `compileall` passed. Python tests could not run in this environment because the available Python runtime lacks `pytest`; no dependencies were installed just for this review.
- `go test ./...` in `go-services/recon` failed at `TestCrawler` with zero results under the default environment, then passed with `ALLOWED_DOMAINS=127.0.0.1,localhost`. This pinpoints a test/config integration issue; it does not prove the full Go/Rust/C++ suite passes.
- AKCA was reviewed through public GitHub documentation, tree listings and sampled verification source. Local `git clone` failed because shell network access was blocked. I did not claim an AKCA test result or measured comparison.

## Priority changes for SecAgent

1. Fix Armada's action routing so `universal_scan` reaches `scan_handler`, and add an integration test that asserts the expected handlers and final coverage manifest for `secagent scan`.
2. Replace canned MCP handlers with real calls, or remove them from the advertised tool list until connected.
3. Use typed proof evidence per check: original request and response, controls, method, payload, canary, replay instructions and proof outcome. Make a missing proof a manual lead rather than a “clean target.”
4. Enforce scope at the HTTP transport and redirect layers, including browser navigation and Go redirects; make TLS verification consistent.
5. Add global request/time/per-host limits and wire `BudgetGuard` into actual LLM calls.
6. Wire browser and API discovery into the default path only when their proof and state safety are ready; require multi-identity and cleanup policies for authorization/state-changing checks.
7. Make sandbox execution real or remove the isolation claim; report skipped tools and failed tasks to the operator.
8. Repair CI tests and produce a reproducible staging corpus before claiming detection or false-positive parity with AKCA.

**Overall judgment:** For an authorized web/API scan today, AKCA appears the safer baseline for evidence-led triage and controlled execution, subject to verifying its published claims in a local benchmark. SecAgent is attractive as an extensible offensive-workflow foundation, but its current default scan path and proof/reporting gaps prevent treating the headline capabilities as delivered scanner coverage.
